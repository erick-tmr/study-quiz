# study-quiz

Arguments: `$ARGUMENTS`

**Organisation.** A **study group** (e.g. `ai-engineer`) is a workspace folder, and
optionally its own git repo on GitHub. It contains **topics** (e.g. `rag`,
`evals`), and each topic contains several **quizzes**:

```
<workspace>/                 # the active study group
  README.md                  # generated index, grouped by topic
  <topic>/topic.json         # {"title", "description"}
  <topic>/<quiz>/quiz.json   # written by you
  <topic>/<quiz>/sources/    # written by you
  <topic>/<quiz>/index.html  # generated by sq.py; never write HTML yourself
```

A quiz is addressed by its key `<topic>/<quiz>`.

## 0. Setup

- **Plugin root**: `${CLAUDE_PLUGIN_ROOT}`. If that is empty, use two directories
  above this skill's base directory (`<base>/../..`).
- **Helper**: `SQ="python3 <plugin root>/app/sq.py"`. Run `$SQ --help` if unsure.
- **State**: run `$SQ status`. It returns JSON with the active `group`, the
  `workspace`, the `git` setting, `is_repo`, `remote`, `topics` (with their quiz
  keys), and `other_quizzes`.

Ask questions with your question tool when one is available (multiple choice);
otherwise ask in plain text. Batch related questions into one ask.

## 1. Management commands (handle these, report, and stop)

| Arguments | Action |
|---|---|
| `groups` | `$SQ group` |
| `group <name>` | If it exists: `$SQ group use <name>`. Otherwise, **create a study group** (§2). |
| `group none` | `$SQ group none` |
| `topics` | `$SQ topic` |
| `topic <name> [title/description]` | `$SQ topic new <name> --title … --description …`, or `topic set` if it exists |
| `git on` / `git off` | `$SQ config git true` (then §2 step 3 if there's no repo yet) / `$SQ config git false` |
| `init-repo` | §2 step 3 for the active group |
| `config` | `$SQ config` |

## 2. Create a study group

1. Confirm the name, in kebab-case. Run `$SQ group new <name>`, which creates
   `~/study-quizzes/<name>` (or `--path` if the user wants another location) and
   makes it the active group.
2. Ask in one batch:
   - **Version this group in git?** (yes / no)
   - If yes, **create a GitHub repo for it?** (yes / no, keep it local)
   - If GitHub: **public or private?** Don't pick a default for them. Public
     means anyone can see the quizzes and their `sources/`.
   - If GitHub: **repo name**, suggesting `<gh user>/<group name>` (get the user
     from `gh api user --jq .login`).
3. Apply the answers:
   - no git → `$SQ config git false`
   - git, local only → `$SQ init-repo`
   - git + GitHub → `$SQ init-repo --github <owner/name> --visibility <public|private> --description "<subject> study quizzes (study-quiz)"`

     If `gh` isn't installed or logged in, say so, run `$SQ init-repo`, and tell
     the user how to add a remote later (`git remote add origin …`, then
     `/study-quiz:quiz init-repo`).
4. Optionally offer to create the first topics now, for example from the
   subject's syllabus.

If the user generates a quiz when `git` for the active workspace is `null`
(never asked), run step 2–3 for it first. A `null` with no active group means
the top-level workspace. If there are no groups at all, suggest creating one.

## 3. Choose the topic

- `topic=<name>` given → use it (create it with `$SQ topic new` if it's new).
- Otherwise, match the subject against the existing topics in `$SQ status`. If one
  clearly fits, use it and say so. If none fits, propose a new topic name and title
  (and say which existing topic was closest), and create it once the user confirms.
- Topic titles are human-readable ("Retrieval-augmented generation"). Names are
  short kebab-case (`rag`).

## 4. Work out what to quiz on

- Arguments can be a subject, file paths, a folder, URLs, or a mix, plus optional
  `n=<count>` (default 10) and `mix=<mc>mc/<open>open` (default about 60% MC).
- **Files/folders**: read them. **URLs**: fetch them. **A bare subject**: use your
  own knowledge, and if it is specialised or fast-moving, say so and offer to use
  the user's notes instead.
- Avoid repeating questions from the topic's existing quizzes: skim their
  `quiz.json` prompts.
- **from mistakes `<topic>/<quiz>`**: read its `quiz.json` and `attempts.json`.
  Collect wrong MC questions and the `points_missed` of partial/wrong open answers.
  Build a new quiz in the same topic, `<quiz>-review-N`, that tests those ideas
  from **new angles** (rephrased, different scenario). Copy the original `sources/`.

## 5. Write the quiz

Quiz slug: short kebab-case (`[a-z0-9-]`, ≤ 40 chars), unique within the topic
(append `-2`, `-3`, … if needed). Never overwrite another quiz.

**`<workspace>/<topic>/<quiz>/sources/`**: the study material as Markdown or
text. Copy the user's notes, or save cleaned extracts of fetched pages with the URL
at the top. For a bare subject, write `overview.md`, a concise and accurate study
summary of every concept the quiz tests. The grader relies on these files. If the
group's repo is **public**, don't copy copyrighted or private material verbatim;
summarise it in your own words and link the original.

**`<workspace>/<topic>/<quiz>/quiz.json`**:

```json
{
  "slug": "<quiz>",
  "topic": "<topic>",
  "title": "Human title",
  "created": "YYYY-MM-DD",
  "language": "en",
  "sources": ["sources/notes.md"],
  "questions": [
    { "id": "q1", "type": "mc", "prompt": "…", "options": ["…", "…", "…", "…"],
      "answer": 0, "explanation": "Why the answer is right and the tempting wrong option is wrong." },
    { "id": "q2", "type": "open", "prompt": "…",
      "reference_answer": "A model answer in 2–5 sentences.",
      "key_points": ["Atomic idea 1", "Atomic idea 2", "Atomic idea 3"],
      "source_refs": ["sources/notes.md"], "difficulty": "easy | medium | hard" }
  ]
}
```

Quality rules:
- **Language**: match the source material (or the user's request).
- **Coverage**: spread the questions across the material. Prefer the important
  concepts over trivia.
- **MC**: 3–5 options with exactly one correct one. Distractors should be plausible
  misconceptions. Vary the position of the correct answer. No "all of the above".
  `answer` is the 0-based index.
- **Open**: explanation, comparison, application or "why" questions. 2–5
  `key_points`, each one independently gradable idea. Together they define a
  full-score answer.
- Mix difficulties. Ids are `q1…qN`.

## 6. Save

Run `$SQ save <topic>/<quiz>`. It validates the quiz (fix any errors it lists and
run it again), writes the standalone `index.html`, regenerates `README.md`, and, if
git is on, commits and pushes when a remote exists. Report the git result,
including any push failure.

## 7. Serve

Check `curl -s localhost:8765/api/health`:
- It answers with `"app": "study-quiz"` and either `"follows_active_group": true`
  or the same `workspace`: reuse it.
- Nothing answers: start `python3 "<plugin root>/app/server.py"` in the
  background (no `--workspace`, so it follows group switches). Don't wait on it.
- Anything else on that port: start it with `--port 8766` (or the next free port)
  and use that port.

Then tell the user, briefly:
- the study group and topic
- the URL `http://localhost:8765/quiz/<topic>/<quiz>` (Claude grades open answers,
  about 15–40s each, on their Claude Code login; the model is set by
  `STUDY_QUIZ_GRADER_MODEL`, default `sonnet`)
- the offline page `<workspace>/<topic>/<quiz>/index.html`
- the MC/open question counts, and the git result
- that `/study-quiz:quiz from mistakes <topic>/<quiz>` builds a review quiz
